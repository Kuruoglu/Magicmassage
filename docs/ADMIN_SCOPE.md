# Admin Scope

Этот документ является коротким источником правды для задач по будущей
админке Magic Massage Natali. Если задача касается админки, Supabase, ролей,
клиентов, календаря, блога, финансов или Stripe-отчетов, начинайте с этого
файла, а не со старого first-release MVP scope.

## Цель

Сделать закрытую admin/CRM-платформу, которая соединена с публичным сайтом и
позволяет управлять контентом, клиентами, записями, сертификатами, медиа,
контактами, блогом, настройками и финансовыми отчетами без изменения кода.

Текущий публичный сайт остается отдельной рабочей линией до начала внедрения
админки. Целевая admin-версия заменяет Studio24 собственной записью через сайт,
но онлайн-оплата услуг массажа не входит в v1. Онлайн-платежи в v1 относятся
только к подарочным сертификатам.

## Видение Дизайна Админки

Админка должна выглядеть как спокойный рабочий кабинет для ежедневной работы,
а не как маркетинговая страница салона. Визуально она должна быть связана с
брендом Magic Massage Natali, но быть плотнее, быстрее и практичнее публичного
сайта.

Основное ощущение интерфейса: "тихая премиальная CRM для wellness-салона".
Интерфейс должен помогать быстро принимать решения: кто записан сегодня, какие
заявки ждут подтверждения, какие сертификаты оплачены, что нужно отправить,
какие Stripe-продажи выгрузить для налогов.

### Визуальная Система

- Базовый стиль: светлый, операционный, data-dense dashboard.
- Фон: warm ivory или pale lavender-gray, близко к публичному сайту.
- Рабочие поверхности: белые панели с тонкой границей и мягкой тенью.
- Основной текст: графитовый, без низкоконтрастного серого.
- Акцент: фирменный salon purple для primary actions, активных пунктов меню,
  фокуса и выбранных состояний.
- Статусы: зеленый для завершено/оплачено, янтарный для ожидает/черновик,
  красный для отменено/ошибка, серый для архив/истек.
- Скругления: компактные, около 8px для рабочих карточек, таблиц, фильтров и
  кнопок. Админка не должна наследовать большие декоративные радиусы hero-блоков.
- Иконки: Lucide или другой единый SVG-набор. Не использовать emoji как
  навигационные или статусные иконки.
- Типографика: sans-serif для рабочих экранов, tabular numbers для денег, дат,
  времени и метрик. Serif можно оставить только для маленького брендового
  акцента в логотипе.
- Не использовать: hero-секции, декоративные blobs/orbs, большие фотоблоки,
  маркетинговые баннеры, перегруженные gradients, неон, beauty-pink стиль.

Рекомендуемые admin-токены должны быть производными от публичного сайта:

- `admin-bg`: очень светлый ivory/lavender;
- `admin-surface`: white;
- `admin-surface-muted`: pale lavender;
- `admin-text`: graphite;
- `admin-muted`: muted gray-purple;
- `admin-primary`: salon purple;
- `admin-primary-strong`: deep purple;
- `admin-border`: soft purple-gray line;
- `admin-success`, `admin-warning`, `admin-danger`, `admin-info`: семантические
  цвета для статусов.

### Общая Компоновка

Desktop layout:

```text
┌ Sidebar ─────────┬ Header: поиск / дата / роль / профиль ─────────────┐
│ Дашборд          │                                                     │
│ Клиенты          │  Заголовок раздела      [Основное действие]         │
│ Пользователи     │  Фильтры / tabs / быстрые статусы                  │
│ Сертификаты      │                                                     │
│ Календарь        │  Основная рабочая зона: таблица / календарь / форма │
│ Виды массажа     │                                                     │
│ Прайс            │  Правая панель: детали выбранного объекта           │
│ Медиа            │                                                     │
│ Контакты         │                                                     │
│ Блог             │                                                     │
│ Финансы          │                                                     │
│ Настройки        │                                                     │
└──────────────────┴─────────────────────────────────────────────────────┘
```

- Sidebar постоянный на desktop, с компактным логотипом и сгруппированными
  разделами: Операции, Контент, Финансы, Система.
- Header содержит глобальный поиск, дату/быстрый переход к сегодняшнему дню,
  роль пользователя и меню профиля.
- Главная область строится из заголовка, primary action, фильтров, основной
  таблицы/календаря и optional right detail panel.
- Для часто используемых разделов использовать split-view: список слева,
  детали справа. Это важнее декоративных карточек.
- Не вкладывать карточки в карточки. Страницы должны быть full-width рабочими
  зонами с отдельными панелями только там, где это помогает сканировать данные.

### Навигация И Роли

- Владелец видит все разделы.
- Администратор видит операционные и контентные разделы без критических
  системных настроек.
- Специалист после входа попадает сразу в календарь или список своих записей.
- Редактор после входа видит услуги, медиа, контакты и блог.
- Бухгалтер после входа видит только раздел "Финансы" и профиль. Sidebar для
  бухгалтера не должен показывать клиентов, календарь, контент, пользователей
  или настройки.
- Недоступные действия не должны просто скрываться на клиенте; права должны
  подтверждаться на сервере и в RLS.

### Ключевые Экраны

Дашборд:

- Верхняя строка: записи сегодня, новые заявки, ожидающие подтверждения,
  оплаченные сертификаты, Stripe-продажи за месяц.
- Ниже: ближайшие записи, задачи, последние сертификаты, быстрые действия.
- Дашборд должен быть компактным. Не делать большой hero-блок.

Календарь:

- Режимы: день, неделя, список.
- Цветные статусы записей: ожидает, подтверждена, завершена, отменена, не пришел.
- Правая панель показывает детали выбранной записи: клиент, услуга, время,
  статус, заметки, связанные сертификаты.
- Основные действия: создать, подтвердить, перенести, отменить, завершить.
- Нельзя полагаться только на цвет; статус должен иметь текстовую метку.

Клиенты:

- Основной вид: таблица или list-detail.
- Поиск по имени, телефону, email; фильтры по тегам, языку, активности.
- Карточка клиента: контакты, язык общения, история визитов, сертификаты,
  заметки, согласия, GDPR-действия.
- Клиентские заметки должны быть визуально отделены от финансовых данных и не
  доступны роли Бухгалтер.

Сертификаты:

- Таблица: код, покупатель, получатель, сумма, статус, Stripe ID, дата оплаты,
  дата истечения.
- Детали: PDF, повторная отправка, погашение, связь с записью, история действий.
- Статусы должны быть сканируемыми chips/badges.

Финансы:

- Это отдельный строгий экран без лишнего декора.
- Верх: выбор периода, кнопки CSV/XLSX/PDF, дата последней выгрузки.
- Summary row: gross, refunds, Stripe fees, net, количество платежей.
- Таблица: дата, платеж, код сертификата, покупатель, gross, fee, net, refund,
  status.
- Для Бухгалтера это единственный рабочий раздел.
- Все выгрузки должны показывать понятное подтверждение и попадать в audit log.

Контентные разделы:

- Услуги, прайс, контакты и блог должны использовать одинаковую структуру:
  список, фильтры, статус публикации, форма редактирования, языковые tabs.
- Для переводов использовать tabs `bg`, `ru`, `ua`, `en` с индикатором
  заполненности.
- Публикация должна быть отдельным действием, не автоматическим side effect
  сохранения черновика.

Медиа:

- Grid с превью, но без декоративной галереи.
- Обязательные поля: alt-текст, папка/категория, отметка разрешения на
  публикацию, где используется файл.
- Действия с медиа должны показывать, где файл уже используется, чтобы не
  удалить изображение с публичной страницы случайно.

Настройки:

- Делить на понятные группы: бизнес-информация, запись, платежи, email,
  privacy/cookies, SEO, пользователи/роли.
- Опасные действия отделять визуально и подтверждать через dialog.

### Формы И Состояния

- Все поля должны иметь видимые labels, а не только placeholders.
- Ошибки показывать рядом с полем и в summary для длинных форм.
- Для длинных форм нужен autosave draft или явное предупреждение при закрытии
  с несохраненными изменениями.
- Primary action один на экран: "Создать запись", "Сохранить", "Опубликовать",
  "Выгрузить отчет".
- Destructive actions отделять от primary actions и подтверждать.
- Loading longer than 300ms должен показывать skeleton или понятный progress.
- Empty states должны объяснять, что делать дальше: создать первую услугу,
  добавить клиента, загрузить медиа, выбрать период.

### Mobile И Responsive

- Desktop является основным рабочим форматом для админки.
- На mobile sidebar превращается в drawer или compact navigation.
- Таблицы превращаются в списки карточек с ключевыми полями и actions menu.
- Календарь на mobile по умолчанию показывает день или список, не плотную
  недельную сетку.
- Touch targets минимум 44px, без горизонтального скролла страницы.
- Fixed header/navigation не должны перекрывать формы и списки.

### Доступность И Качество

- Контраст текста минимум WCAG AA.
- Keyboard navigation обязательна для sidebar, таблиц, календаря, dialogs,
  tabs, filters и форм.
- Focus states должны быть видимыми.
- Reduced motion должен отключать декоративные transitions.
- Не передавать смысл только цветом; рядом со статусом нужен текст или icon +
  label.
- Все icon-only buttons должны иметь aria-label или видимый tooltip.
- Денежные значения, даты и время должны быть выровнены и легко сравнимы.

## Модули V1

- Дашборд: записи на сегодня, новые заявки, ближайшие визиты, ожидающие
  сертификаты, новые клиенты и быстрые действия.
- Клиенты: имя, телефон, email, язык общения, заметки, история записей,
  сертификаты, теги, согласия, экспорт и удаление по GDPR.
- Пользователи: сотрудники админки, роли, приглашения, блокировка доступа и
  журнал входов.
- Сертификаты: Stripe-оплата, PDF, отправка, повторная отправка, ручная выдача,
  статусы и погашение по коду.
- Календарь: рабочие часы, выходные, перерывы, блокировки времени, создание,
  перенос и отмена записей.
- Виды массажа: категории, локализованные названия и описания, SEO, фото,
  длительность, видимость на сайте.
- Прайс: варианты услуг, длительность, цена, валюта, активность, порядок вывода
  и история изменения цен.
- Медиа: загрузка фото и документов, папки, alt-тексты, превью и отметка
  разрешения на публикацию.
- Контакты: адрес, телефон, email, Telegram/Viber, соцсети, часы работы, карта и
  LocalBusiness SEO.
- Блог: статьи, категории, теги, автор, обложка, SEO, черновик, публикация,
  отложенная публикация и локализации.
- Финансы: Stripe-продажи за период, комиссии, возвраты, net-суммы и экспорт
  для налогов.
- Настройки: языки, SEO по умолчанию, правила записи, email-шаблоны, Stripe,
  карта, cookie/privacy тексты и audit log.

## Роли

- Владелец: полный доступ ко всем разделам, ролям, настройкам, платежам,
  отчетам и audit log.
- Администратор: клиенты, записи, календарь, сертификаты, услуги, прайс, медиа,
  контакты и блог; без критических системных настроек.
- Специалист: календарь, свои записи, базовая информация о клиентах и статусы
  визитов; без финансовых отчетов и настроек сайта.
- Редактор: услуги, медиа, контакты, блог и SEO-контент; без клиентов,
  календаря, платежей и пользователей.
- Бухгалтер: только финансовые отчеты по Stripe и связанные продажи
  сертификатов; без редактирования сайта, клиентов, записей, сертификатов,
  пользователей или настроек.
- Просмотр: read-only доступ к разрешенным разделам без экспорта персональных
  или финансовых данных.

## Бухгалтер И Stripe-Отчеты

Бухгалтер должен иметь возможность выбрать период и выгрузить все Stripe-продажи
за этот период для налогов. Период считается по timezone бизнеса в Болгарии:
`Europe/Sofia`.

Отчет должен включать:

- дату платежа;
- Stripe PaymentIntent/Charge ID;
- код сертификата;
- покупателя и email покупателя;
- gross-сумму;
- валюту;
- комиссию Stripe;
- net-сумму;
- статус платежа;
- возврат и дату возврата, если есть;
- описание или назначение платежа.

Итоги отчета должны показывать общие продажи, количество платежей, сумму
возвратов, комиссии и net к выплате. Форматы экспорта: CSV, XLSX и PDF-сводка.
Каждая выгрузка логируется в audit log: кто скачал, когда, за какой период и в
каком формате.

В отчете нельзя показывать card data, CVC, полные платежные реквизиты,
внутренние клиентские заметки или процедурные комментарии. Секретный Stripe key
используется только на сервере.

## Связь С Публичным Сайтом

- Публичный сайт должен получать управляемые данные из админки: услуги, цены,
  контакты, медиа, блог, сертификаты и настройки.
- Публичные языки остаются `bg`, `ru`, `ua`, `en`; для `ua` SEO-метаданные
  используют `uk-UA`.
- Контент можно публиковать только после заполнения обязательных полей и нужных
  языковых версий.
- После изменения публичного контента админка должна обновлять страницы сайта,
  sitemap, SEO metadata и `hreflang`.
- В целевой admin-версии кнопки записи открывают внутренний flow записи вместо
  Studio24.
- Публичная запись по умолчанию создает заявку со статусом "ожидает
  подтверждения"; администратор подтверждает, переносит или отменяет ее.

## Технические Ориентиры

- Next.js App Router и TypeScript для публичного сайта и `/admin`.
- Supabase/PostgreSQL для данных.
- Supabase Auth для входа и приглашений.
- Row Level Security для защиты данных по ролям.
- Supabase Storage для медиа.
- Stripe для оплаты подарочных сертификатов и финансовых отчетов.
- Email provider, например Resend, для отправки сертификатов и уведомлений.
- Audit log для входов, публикаций, изменений, отмен, погашений сертификатов и
  финансовых экспортов.

## Не Входит В V1

- Личный кабинет клиента.
- Онлайн-оплата услуг массажа, депозиты или предоплаты за записи.
- Telegram booking flow.
- Loyalty, бонусы, промокоды и абонементы.
- Мультисалонность и франчайзинговая структура.
- Полная бухгалтерия вместо Stripe-отчета.
- AI-переводы как production workflow.

## Критерии Приемки

- Владелец может управлять admin-контентом без изменения кода.
- Публичный сайт корректно показывает данные из админки во всех четырех языках.
- Пользователь без нужной роли не может открыть или изменить закрытые данные.
- Бухгалтер видит только финансовый раздел и может выгрузить Stripe-продажи за
  выбранный период.
- Финансовый отчет корректно учитывает успешные платежи, комиссии, net-суммы и
  возвраты.
- Нельзя создать две записи на одно и то же время.
- Сертификат после оплаты появляется в админке, получает статус, PDF и может
  быть использован в записи.
- SEO, sitemap, canonical и `hreflang` обновляются после публикации контента.

## Тесты

- Unit-тесты для ролей, прав доступа, финансовых расчетов и статусов записей.
- Интеграционные тесты для Stripe webhook, Stripe export, сертификатов и
  admin-actions.
- Playwright smoke для входа в админку, проверки роли Бухгалтер, создания
  записи, работы сертификата и CRUD услуг, цен и блога.
- Проверки приватности: card data не хранится, секреты не попадают в клиентский
  bundle, финансовый экспорт доступен только роли Бухгалтер и владельцу.
